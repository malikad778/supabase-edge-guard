# Suppressing Findings and Baselines

`supabase-edge-guard` strives for near-zero false positives. However, there are legitimate application designs where a pattern flagged by a rule is safe and intended.

The tool provides two mechanisms to handle these cases:
1. **Inline & file-level suppressions** (with a mandatory reason).
2. **Baselines** (to adopt the tool on existing codebases without fixing all technical debt first).

---

## 1. Inline Suppressions

### Next-line suppressions

To suppress a finding on the immediate next line:

**TypeScript / JavaScript:**
```ts
// edge-guard-disable-next-line SG001 -- session is only read for user preferences (theme/locale), not authorization
const { data: { session } } = await supabase.auth.getSession();
```

**SQL Migrations:**
```sql
-- edge-guard-disable-next-line SG010 -- static reference table containing public zip code data, writes forbidden by DB role
CREATE TABLE public.zip_codes (
  code text primary key,
  city text not null
);
```

### File-level suppressions

To disable a rule across an entire file, place the directive at the top of the file:

**TypeScript / JavaScript:**
```ts
// edge-guard-disable-file SG002 -- administrative worker running in isolated background queue with internal HMAC auth
```

**SQL Migrations:**
```sql
-- edge-guard-disable-file SG005 -- legacy migrations generated by third-party tool, will not modify historical files
```

### Multiple Rules

You can suppress multiple rules by comma-separating their IDs:

```ts
// edge-guard-disable-next-line SG001, SG002 -- caller verified via separate custom session token
```

---

## 2. Mandatory Reason Requirement

Every suppression directive **must** provide an explanation following `--`:

```
// edge-guard-disable-next-line <RULE_ID> -- <REASON>
```

If a suppression comment omits the `-- <REASON>` section:
- The suppression is **ignored**.
- An `info` finding **`SG000 (SuppressionWithoutReason)`** is emitted at that line.

This ensures all exceptions are documented, auditable in code reviews, and prevents developers from blindly silencing warnings without review.

---

## 3. Configuration Disables

To disable a rule globally across your entire project, update your `supabase-edge-guard.config.json` (or `.supabase-edge-guardrc.json`):

```json
{
  "rules": {
    "SG011": "off",
    "SG005": "info"
  }
}
```

Allowed values for each rule:
- `"error"`: fail the build if `--fail-on error` (default).
- `"warning"`: emit a warning.
- `"info"`: emit an informational finding.
- `"off"`: completely skip running this rule.

---

## 4. Baselines

When introducing `supabase-edge-guard` into a large or legacy codebase with dozens of existing issues, fixing everything in one PR may be impractical.

### Generating a Baseline

Run the `baseline` command to capture the project's current state:

```bash
npx supabase-edge-guard baseline
```

This generates `.edge-guard-baseline.json` in your project root, containing all current findings.

### Scanning with a Baseline

Subsequent scans will automatically detect `.edge-guard-baseline.json` and hide any findings recorded in the baseline:

```bash
npx supabase-edge-guard
```

Only **new** security issues introduced after the baseline was generated will be reported.

To bypass the baseline and view all findings:

```bash
npx supabase-edge-guard --no-baseline
```

### How Fingerprinting Works

Baselines do not rely on line numbers. Each finding is fingerprinted using a SHA-1 hash of:
```
sha1(ruleId + ":" + normalizedFile + ":" + normalizedSnippet)
```

Because the fingerprint uses the code snippet rather than the line number, code edits elsewhere in the file that shift lines up or down will **not** invalidate the baseline entry.
